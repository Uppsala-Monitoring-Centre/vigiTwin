# Migration: clinical dates take their own offset (1.2.3)

Publication mode used one whole-day offset for every date in a pair. It now
uses two — one for report dates, one for the clinical history — and the
default policy changed with it. Nothing in the evidence pipeline, the
classifier or the internal review is affected; this is the publication
transform only.

## Why

A report date is pinned near its reporting-context year, because the
contextual counts on the page are real and belong to that country-year. A
clinical history mixing year-, month- and day-precision dates can usually
only move by whole years, because anything else changes what the page says
about the order of a bare `2006` and a `2006-05-30`. One offset had to
satisfy both.

For a real pair carrying sixteen dates across twelve years, exactly three
offsets satisfied the invariants — `-365`, `0` and `+365` — and the published
supplement carried the patient's real timeline. Reports routinely arrive
years after the events they describe, so there was never a reason for the two
to move together.

## What changed

| | Before | After |
|---|---|---|
| `policy_version` | `1.0` | `2.0` |
| `date_offset_min_days` | `0` | `30` |
| `date_offset_candidates` | `1024` | `2048` |
| clinical dates | the report-date offset | `clinical_offset_*`, either direction, up to 5 years |
| a coarse date held while precise ones move | a hard failure | a `coarse_date_drift` advisory |
| zero offset | a draw like any other | tried last, after every band |
| a floor | excluded smaller offsets outright | preferred, with `date_offset_below_floor` when unreachable |

New policy fields: `decouple_clinical_dates` (default `True`),
`clinical_offset_min_days` (30), `clinical_offset_max_days` (1826),
`clinical_offset_backward_only` (`False`), `allow_coarse_date_drift`
(`True`).

New artifact fields, both additive: `clinical_offset_days` on each case of the
scrambling key record, and `clinical_offset_bound_days` on the public
transform manifest (`null` where the two blocks were solved together). The
key record's `schema_version` stays `1.0` — the fields are optional, and a
reader of the old shape still parses the new one.

One new advisory code, which does not block: `date_offset_below_floor`, for a
case whose relationships admitted nothing larger than a sub-floor offset. The
same release adds `approval_digest_mismatch`, which **does** block; that one
belongs to the approvals change rather than this one.

## What you have to do

**Nothing, if you have not published a supplement yet.** Run as before; the
new defaults apply.

**Re-running an earlier study will not reproduce its offsets.** The draw seed
now includes which block is being solved, so the same salt and the same pair
give different offsets than they did under 1.2.x. A supplement already
published cannot be regenerated byte-identically by this version. If you need
the old offsets, the scrambling key record for that run holds every one of
them, and the git tag for the version that produced it is the code that drew
them. Do not try to reconstruct them from a policy file.

**Check your policy file for the two floors.** A policy that pinned
`date_offset_min_days=0` and `date_offset_max_days=0` to hold dates still
(there are tests that do this deliberately) must now also pass
`decouple_clinical_dates=False`, or the clinical block will move on its own.

**Expect a new sentence in the footer.** A run whose blocks took different
offsets says so on the page: the interval between an event and the report
describing it is not the reported interval. This is the one quantity the
split gives up, and it is stated rather than left for a reader to assume.
